# TRAINING_ALGORITHM.md

How this project turns compute and attention into a stronger bot. Year-agnostic: it names no unit, mechanic or tool of a
particular season (CLAUDE.md and HANDOFF.md map it onto this repository). It distils six practice seasons and the
cross-year advice; where they disagreed, the later season and the measured result won.

## 0. Objective and instruments

**Objective: absolute strength against the external field** (ladder rating and expected score against every field bot).
Beating our own earlier builds is a means, never the goal. A change is worth what it moves against the field.

Every decision names the instrument that makes it. Each sees something the others cannot:

| instrument | answers | blind to |
|---|---|---|
| rules digest (engine source, verified) | what is possible, exactly | what matters |
| replay reader + census + the bot's own counters | why one game went as it did; whether a mechanism fired | statistics |
| mirror (candidate vs incumbent, paired seeded cells) | regressions, crashes, cost of a change | anything both builds share; anything only the field does |
| sparring archetypes (our copies of field tactics) | does a change survive or exploit that tactic | everything else |
| external ladder (official-format replica, batch rating) | are we stronger; what the field punishes | small effects at small N |
| frozen roster of our snapshots | is the lineage walking downhill | the field |

When two instruments disagree, that is a finding: run the third, report the disagreement, never pick the convenient one.

## 1. Phase 0: foundations before strategy

Nothing is tuned until every item below exists and has passed a check on a case whose answer is known.

1. **Rules digest** with the engine location of every fact. Read the ending of one starter-bot game. Census the map
   corpus (sizes, symmetry types, spawn geometry, resource placement). Tally how games are actually decided.
2. **Runner**: headless, bare JVM, parallel, private class tree per run, wall-clock cap, results keyed by (code hash,
   opponent, map, side, seed) with the end reason. Patch a per-game seed if the engine lacks one. **Determinism check**
   (identical inputs give identical games; list every residual randomness and exclude those outcomes from paired
   counts) and an **identity control** (a byte-identical copy reads 0 discordant pairs) on every verdict path.
3. **Replay reader**: per-round team aggregates, one robot's life, board at a round, event windows, the bot's own
   counters, bytecode by type, navigation statistics, and one census row per team per game. Fixture tests.
4. **Bot iteration 0**: layered code (turn loop, globals, constants with provenance, comms schema, map memory, navigation,
   one handler per unit type); a monitor for overruns, near misses and caught exceptions from the first commit;
   decision counters in the bot's self-report; per-robot RNG; tie-breaks relative to the robot's own geometry; unit
   tests of pure logic (encodings, schema layout, symmetry inference on synthetic and real maps).
5. **External field**: scripted discovery, automated safety scan, blind compile, final-bot choice by name and
   metadata, content-hash dedupe, smoke test, calibration games for every new bot. Never read their source.
6. **Ladder and views**: the official-format ladder replica; a batch pairwise rating (each build its own player,
   repeated cells counted once, pairs capped, iterated to convergence); charts, ladder pages and the handoff
   regenerated by one post-block command.
7. **Basics battery**, run on every block: absolute bars (0 overruns, 0 exceptions, symmetry never wrong and decided
   within the offline bound) and relative bars against a control (economy delivered and not floating, no starving
   producer, stuck/oscillation rates, combat tempo), relative bars failing only beyond 2 paired SE.

**Foundation bar** (before the loop): beats the starter bot from both sides on every map, passes the basics battery,
is placed on the ladder. Then run the first **correctness audit** (§4) and only then start the loop.

## 2. The loop

1. **Pick a target**, rotating among sources so none dries up:
   - *own degeneracies*: a counter that never fires, a unit latched in one state, a resource pinned unspent, a producer
     starved, an overrun. Highest yield; needs no opponent.
   - *the field*: how the bots just above us win (their games are free to study); a two-group contrast of behaviour
     rates (bots that beat us vs bots we beat; keep only rates where we differ from the first group and match the
     second); the tactic that beats us, copied.
   - *capability gaps*: an engine method or mechanic never used; a cross-year principle not yet applied.
   - *a structural swing* (§4).
   Prefer repairs, cap removals and changes that cost nothing; reallocations between unit types rarely transfer.
   After three rejects in one functional area, the next candidate comes from another area. At least one structural
   attempt in every four.
2. **Trace before theorising.** Read the motivating replay with the reader; confirm in a second game against a
   different opponent; count how often the trigger occurs across recent games; check we are actually behind on the
   quantity.
3. **Pre-register** in the log: mechanism, its decision counter, reachability (the branch is taken at observed values,
   the choice set has more than one member), expected firing rate, price (what it displaces), the deciding instrument,
   the gate, the falsifier, and for numeric changes a dose ladder including a zero arm.
4. **Implement one change behind a switch**; the working bot at defaults plays exactly as the incumbent. Tests pass;
   the arm is proven to differ from the incumbent exactly as intended.
5. **Show delivery before judging value**: (a) one logged diagnostic game where the mechanism can fire (maps and sides
   may be chosen for diagnostics); (b) a paired delivery mini-block: the mechanism fires and its signature reaches the
   target. Verdicts are three-way (pass at 1 SE beyond the bar, fail at 2 SE short, otherwise extend). Tools refuse the
   gate until delivery passes. A mechanism that delivers its proxy can still lose: pair the signature with an outcome
   guard.
6. **Gate** on seeded paired cells against the incumbent over the band of field bots nearest our rating, judged on the
   most informative per-pair statistic, with sequential looks, ship and stop rules fixed in advance and their power
   simulated. The mirror is a regression screen; changes aimed at a field behaviour also face the archetype that has
   it. An overrun or a new exception voids an arm.
7. **Accept**: snapshot as a frozen package; enter the ladder as a new player and calibrate; play the frozen roster;
   run the post-block command (ratings, charts, pages, census, ledger, handoff); commit and push in the same step.
8. **Reject**: restore the incumbent byte for byte; ledger entry with the closing number, the kind of closure and a
   testable re-open condition. Positive near-misses with independent mechanisms are kept to be stacked and tested as a
   new arm. Never stack on mere non-inferiority.

## 3. Statistics that keep the loop honest

- The unit of evidence is the paired cell (opponent, map, side, seed), not the game; only discordant pairs inform.
- Never read a running batch; never move a bar after seeing a number; never reinterpret a null.
- First looks and small blocks regress toward zero. A fixed-seed single game is a filter, never a verdict.
- Compare a candidate with controls played in the same period on the same pool, never with the incumbent's history.
- State the unit of every margin (a win-minus-loss margin has twice the spread of a win count).
- A correlation earns a diagnostic, not a code change; act only on the earliest round at which a metric predicts the
  result; stratify within map and opponent.
- Decide the inconclusive band in advance. Before relying on a gate, simulate its power at the effect sizes we
  actually produce; a gate that cannot pass a real gain is a defect.

## 4. Plateau protocol and big swings

When accepts stop, escalate in this order and do not skip steps:
1. **Correctness audit of the bot and the instruments**: independent lenses (dead code and unreachable branches;
   rules and API, including information the engine gives away; shared state and staleness; behaviour seen in replays;
   the measurement pipeline), each finding with evidence, a fix and a regression test, reviewed by adversarial
   verifiers. Fix instruments first, prove them with an identity control, then judge the bot fixes together. One
   broken basic is a sample of a class.
2. Ablate what we carry (thin-margin accepts are often worth nothing; failure-mode preventers often the most).
3. Sweep the engine API and mechanics for anything unused.
4. Re-read the field's games for what we were not looking for; copy the offence that beats us, then build the
   defence against our own copy.
5. Re-read the cross-year principles.
6. Look for jointly necessary pairs; stack positive near-misses.
7. A structural attempt or a rewrite: keep the plumbing and the proven parts, design on paper from census numbers,
   set a stage budget and a kill criterion, probe the ladder early.

## 5. Operations

- **Never idle.** The compute machine always has work: at least three items queued, and an idle filler (ladder
  scrimmages among field bots, budgeted by the information they add). Waiting on a run is time to read replays, prepare
  the next arm, or audit. Never stop to wait for an idea or an approval.
- One semaphore for every path that starts games; private class trees; scripts re-exec from private copies; kill by
  process id, never by a pattern that can match the caller; disk checked before every block; replays pruned by what
  their consumers still need.
- Every rule that can be forgotten becomes a tool that refuses. Unit tests run after every change to the bot or a tool.
- Records: an append-only training log (one entry per attempt, with run ids so a fresh session can resume); a
  closed-directions ledger; a short learnings file in which every lesson names its measurement; a handoff that is a
  closure map. Record measurements, not explanations. Nothing stale stays.
- Push after every commit. Record every owner prompt verbatim.

## 6. Working with the owner

Act without approval on bot and method decisions. Answer questions from code and data, never from memory; treat a
short basic question as an audit trigger. When a rule (the owner's or our own reading of it) blocks progress, bring
its measured cost and a recommendation instead of silently keeping the stricter reading. Keep everything the owner
reads current on every accept: the ladder view, the charts, the handoff.

## 7. Defaults (tune by measurement, record the change in the log)

| parameter | default |
|---|---|
| near-miss bar | 90% of the per-turn compute limit, measured before any deliberate budget fill |
| delivery mini-block | 24 paired cells, extended to 48, 96, 192 while inconclusive |
| mirror screen | sequential test on discordant pairs, p0 0.50, p1 0.58, alpha = beta = 0.05, batches of 16, cap 320 pairs |
| band | the 20 field bots rated nearest the incumbent; refreshed with fresh seeds at every accept |
| ship rule | looks at 240 / 480 / 720 paired cells; ship at t >= 3.0 at the first look or t >= 2.3 later with net wins >= 0; stop when t < 0.5 at look 1 or < 1.0 at look 2 (re-simulate power before first use) |
| pair cap in the rating fit | 200 games per pair |
| rejects before leaving an area | 3 |
| structural attempts | at least 1 in every 4 |
| concurrency on the compute machine | measured knee (cores minus one by default); 1 diagnostic game on the session machine |
