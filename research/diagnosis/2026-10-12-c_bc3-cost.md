# c_bc3 cost and guard diagnosis — 2026-10-12

The official VM probe confirms some method savings and budget-dependent changes to predicted well lists. **c_bc3 is
not universally decision-preserving.** Completed-pass lists agree in these fixtures at ample budget; finite-budget
lists do not. Keep c_mend2 validated until the observed call distribution and the changed behavior justify an arm.

## Evidence and provenance

The zero-game probe ran on battlecode-dev with the checksum-pinned official 3.0.15 jar and VM JDK 8. It used only our
frozen c_bc3 (`ed3aceb26a90`) and c_mend2 (`d62033781fbd`) source, private class trees and the engine's
`TeamClassLoaderFactory`. No opponent source, game, ladder submission or shared bot build was involved.

Driver artifacts: `build/codex-recovery/cbc-probe-20261012T210624Z/`, including `result.json`, `provenance.json` and
the owned probe source. Result SHA-256:
`a4790bac26035bca89a77ea46c956febe54d4ace24b0ec401a3e687ae1a3edde`.
The official engine SHA-256 is `5d4e42a51946cc1c2149426485bda8096ff1c088c77e3ed075c06ce5968ed72a`.

The measured interval is `computePredWells` itself, excluding host setup, proxy implementation, class initialization,
background work and telemetry. It includes instrumented own instructions, array accounting and API call-site
charges. A separate owned fixture verified `readSharedArray`/`onTheMap` wrapper costs of 5/8: three wrapper
instructions plus the engine table's 2/5 API charges. Every return had zero pending bytecode debt. Initialization
costs are recorded separately, rather than silently included in method costs.

There are 192 fixed cases: six well/HQ shapes, four prior-state conditions and eight entry budgets. Each was repeated
twice: **zero measurement drift**, **58 differing finite-budget lists**, **zero differing lists at budget 1,000,000**.
Exact coordinates, shared slots, symmetry, output lists, timer/key state and costs are in the artifact. The local
source-built prototype was explicitly marked non-release evidence; the independent official VM run confirmed it.

Only two of six shapes delivered a cheaper cache hit after the 10k warmup. That is a fixture count, **not a field
frequency or expected saving**. Ample-budget equality also does not establish finite-budget equivalence of the
timer, cache availability or selected raid target. The 1,899,878 Bc3Test cases set the monitor budget through
reflection without counting ordinary test execution; they remain logical tests, not a runtime-cost measurement.

The completed replica panel supplies an outcome guard, not case weights: c_bc3 and c_mend2 each won 61/100, with all
win/loss outcomes unchanged, but 37 durations differed. Candidate island-round margin was -136.8 (t -1.79). There
were no coin cells or observed replay overruns/self deaths; decoded exception turns were zero. Blank indicator
counters do not prove zero main-work near misses. End-turn maxima include discretionary work and cannot replace
this method measurement.

## Where these cases can occur

`Launcher.run` enters `march` only when movement is ready and no enemy is currently hittable. `pickObjective` can
return a nearby shared sighting, a qualifying home recall or an enemy island before reaching raid selection. Only
with an enemy HQ prediction and decided symmetry does it call `raidWell`; that calls `computePredWells` when
`round - predRound >= 20`.

A completed pass or cache hit restarts the 20-round timer. An interrupted pass records `predRound = round - 15`,
so the next eligible attempt is due after five rounds. Movement cooldown and higher-priority objectives can delay
either interval. The optimization can therefore change both work per call and calls per robot-round. Cache reuse
also requires unchanged symmetry, predicted HQ coordinates, shared well locations and the robot's seen-well count.
Dense, repeatedly interrupted states cannot benefit from a key that never finished.

One additional cost sink: `march` calls `pickObjective` before overriding its result for a mending launcher. A mender
can pay for raid prediction that it then discards. Log whether the resulting objective is consumed; do not count
every predicted-well computation as useful delivery.
